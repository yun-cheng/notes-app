# Notes app: plan so far

`notes-app` is a working name. A real name will be picked before the app is shared with anyone.

## Goal

One local-first tool for all personal notes, todos and diary, used on an Android phone and a Mac mini. It may later be shared with other people (family, high school classmates, etc.).

Privacy goal: keep notes private from friends and family. Not defending against forensic or state-level attackers.

Existing apps were considered (Notesnook is the closest, then Anytype, then Obsidian with Meld Encrypt). The owner chose to build their own, as one tool for every need.

## Product decisions

### Cards
Everything is a card: `note`, `todo`, `tag`. (Until 2026-11-14 there was a `diary` card too, one per day; see "The diary is a vault" below.)

- Todo adds status, due date, an optional due time and an optional repeat. Today and Upcoming are filters on the journal.
- A note and a todo are the same entry written two ways, so one click turns either into the other (decided 2026-11-12): a todo's checkbox, due date, time and repeat go when it becomes a note, and a note becomes an open todo with no date. A note with no title gives its first line to the todo's title, and a todo with no details gives its title back as the note's text, so "buy milk" stays "buy milk" both ways. Undo puts back exactly what was there.
- The diary is a vault every account starts with, named Diary. Its entries are notes and todos like any other, dated by when they were written.
- Links and backlinks are in scope. Canvas/whiteboard is NOT needed for now.

### One journal for everything
Decided 2026-11-12, like Logseq's journal. There is one place where everything is written and read: the Journal, a stream of compact bubbles holding notes and todos together, oldest at the top and newest at the bottom like a chat, with a box at the bottom to write the next one. Kinds and places come from markers in the text, not from separate screens, and the box formats them as they're typed: The box, or in its place the view-only bar or the bar for picked entries, stays at the bottom of the screen on a strip of the page's color that reaches the screen's edge (or the tab bar), with a short fade above it, so entries scroll away behind it rather than showing under and past it (`.journal-dock`, 2026-11-17). Where there's no box (the Archive, the Trash, the board) the bar for picked entries keeps its place too, hidden while nothing is picked (`FloatDock`, 2026-11-18; before, it took room only when it showed, moving every entry as the first was picked), and those pages' entries start at the top even in written order, so the bar growing with what's picked (a todo adds buttons) only takes room below them. The title bar's buttons keep an icon button's height whatever they are, so its Select all and Done don't change its height either.

- `[] ` or `TODO ` at the start turns the line into a checkbox (`#todo` makes a todo too); on a todo, `@today`, `@tomorrow`, `@fri` or `@2026-12-01` sets the due date, `@3pm` or `@15:00` the time, and `@daily`, `@weekdays`, `@weekly`, `@monthly`, `@yearly` or `@every-2-weeks` makes it repeat. A time or repeat with no date starts today.
- Each line starting with `[] ` or `TODO ` starts its own entry, so a list of `[] …` lines makes a todo for each. With the box's todo button on, every line is a todo. A last line of only `#tags` applies to all of them.
- `#diary` files the entry in the Diary vault.
- Any other `#tag` files it under that tag, making the tag if it's new.
- Tags can be gathered in groups, made on the Tags page: a group of one choice, like Priority (High, Medium, Low), gives an entry at most one of its tags, so typing or adding another swaps it; a group of any number, like Topics, just gathers its tags. Groups show as their own sections in the sidebar, and a group's tags come first on an entry. In an open entry, clicking a grouped tag opens its group's tags, to switch it in place (High to Low) or clear it; in the journal, a grouped tag in the entry menu's Tags… panel does the same, opening its group's tags under the field, the entry's filled, where one click sets, switches or clears one, and a one-choice group the entry has no tag from shows as "+ Priority" (until 2026-11-18 a grouped tag on a bubble was itself a button for this; now a bubble's tags are only labels). An open entry with no tag from a one-choice group shows a faint "+ Priority" chip to set one. Any tag can have a color, picked from the dot beside it on the Tags page; its chips and its sidebar icon take that color (stored as the tag card's `color`, as on entries). A group is a tag card with `members` (its tags, in order), `choice` and `ordered`; it is never put on entries, and typing its name (`#priority`) adds nothing. Edits from two devices can leave two tags of a one-choice group on an entry; both stay, marked as a clash.
- `#` suggests tags, `@` suggests due dates, a typed time and repeats, and `/` lists what can be added: a todo, tag, due date, the diary, a photo, a list, a quote or a heading.
- Code: ` ``` ` (or ` ```js ` with a language) and a space starts a code block in the box. Inside it Enter is a new line, kept as typed with its indent, and three in a row leave the block; Cmd+Enter saves. The whole block stays in one entry. In an open entry, the formatting row's code button (`</>`) makes the words picked within a line inline code (Cmd+E does too), and otherwise turns the line into a code block, or back; backticks around words make inline code as they're typed. Code blocks are colored by their language, the one after ` ``` ` (js, ts, python, sh, sql, json, css, html, go, rust, swift, kotlin and the rest of highlight.js's common ones, by name or short name), or a guess when there's none; one it doesn't know stays plain. Each code block in an editor has a language picker on its top edge (Auto, the guess, then C to YAML and Plain text, from `src/ui/codeLanguages.ts`); picking one sets the block's language, so the colors follow it and a block made with `</>` needn't be guessed. A short name after ` ``` ` shows as its language (`js` is JavaScript), and one not in the list shows as written. In view only and read-only views the picker is a plain label, hidden for Auto. Bubbles name a snippet's language in a slim strip over the code, on the left, with the copy button on its right (since 2026-11-18; it sat at the top right, on the end of the first line, giving way to the copy button on hover, and then for a moment at the bottom right, where a long last line ran under it); Auto shows none, and gets the strip only on a touch screen, where the copy button always shows. A snippet last in the text leaves no more room under it than text would. The same colors show in bubbles, the writing box, an open entry, read-only views and public links. They come from lowlight (highlight.js), loaded the first time code shows, so the app opens without it (`src/ui/highlight.tsx`, and `src/ui/editor/codeHighlight.ts` for the editors); the colors are theme tokens (`--code-*`) for light and dark.

The journal is filtered from two places. The title bar's second row (`FilterBar` in `src/ui/FilterPanel.tsx`) starts with a switch between All, Notes, Todos and Stacks (a menu chip until 2026-11-17; one press now, and all in sight; Todos keeps a todo status, the others take it off; Stacks, added 2026-11-18, shows only stacks, each with its entries in it, and Notes leaves stacks out, so a stack's notes show on their own there, as its todos do under Todos), then a chip for each of Todos (open, due today, upcoming, no date, waiting, done), Written (today, the past 7 or 30 days, or Pick dates…, a day or range picked in the calendar) and Contains (links, photos or files; a link straight to a picture, like a .jpg, counts as a photo; a page's preview image doesn't), then Templates, a plain switch that swaps the journal for the templates (`template=1`), where the box writes new templates. Each chip opens a small menu of its choices; one in use names its choice, like "Due today", with an × that takes it off, and picking it again in the menu does too. A todo status means todos, so picking one sets Type to Todos as well: taking the status off leaves Todos, and taking Todos off, or picking Notes, takes the status off too. The sidebar keeps what works more like a place: Journal, History, Calendar and Timeline (the last two take Todos, the tag and the vault of a filter), Photos (all but Contains and Templates), Archive and Trash (pages of their own since 2026-11-18; see the notes on archiving), the tags (by group, with their counts, pinned ones as folders) and the vaults. A tag or vault in use shows in the title bar's row too, with its ×, and Clear all, when two or more filters are on, takes them all off. The row scrolls sideways on a phone, and its menus sit fixed so the scroll doesn't clip them. The title bar sits at the very top of the page, scrolled or not, and the scrollbar's room is kept on a page too short to scroll, so a filter that leaves few entries doesn't make the bar jump down or sideways (fixed 2026-11-17: there was room above the bar, which it lost once the page scrolled). Added 2026-11-16, moving type, status, date and contents out of the sidebar, where they made a long list. The journal's top bar sorts it by oldest first, newest first, recently edited, due date, or an ordered tag group with tags (Priority, highest first, each tag under its own heading; a group with none isn't offered), with the order named beside an icon, or the icon alone on a phone. Filters combine. Picking a locked vault asks for its PIN right there. New entries go into whatever the journal is narrowed to; narrowed to one day, they are written on that day. On a phone, the sidebar's tags and vaults open in a sheet from a button in the title bar. Each section's heading folds it, remembered on the device; a folded section still shows the choice in use.

The journal can also show as a board, like Trello's (added 2026-11-16, `src/ui/pages/board.tsx` and `src/domain/board.ts`). Its columns come from one of two places. By todo state (added 2026-11-17, `board=state`), they're Open, Waiting and Done, from each todo's own box and Waiting mark, so no tags are needed: dragging a todo into Done ticks it (a repeating one moves on to its next date and stays), into Waiting marks it waiting, and into Open reopens it or takes waiting off; notes, which have neither, aren't on it, and Done has no Add a card. This is the built-in state the Todos filter reads. By a tag group (`board=<group ID>`), a group's tags are its columns, in the group's order, each holding the entries with that tag: stages of your own, like To do, Doing, In review, which notes can carry too and which nothing changes but you. The filters narrow either board as they narrow the list. The board button beside the sort (on a phone, the sort menu's Board choices, and anywhere Cmd+K's "Show as a board") switches to it, opening the board this device showed last, or the one by todo state; the column menu in the sort's place picks the other kind, another group, Other… (the choices) or the list again, and the board is kept in the address like the sort when filters change. Other… lists the board by todo state and every group with tags; groups are made on the Tags page. (Until 2026-11-17 it offered to make a Status group of To do, Doing and Done, and the demo had one; the board by todo state does that job without tags, so both went.) Entries with none of the group's tags wait in a first column, "No priority", folded by default to a narrow strip with its count, since it can hold most of the journal; any column folds from its heading, remembered on the device. A card is the entry's bubble, and a click opens it. Dragging moves a card: with a mouse from anywhere on it, once it has moved a little; with a finger from its grip (bottom right on a touch screen, so a swipe elsewhere still scrolls); and from the keyboard with the arrow keys on its grip, up and down in its column and left and right to the next column's end. A copy follows the pointer, a gap shows where it will land, the board and its columns scroll near their edges, and Escape cancels. Dropped in another column, the card's tag in the group is swapped for that column's (in a many-choice group only the column it left is swapped, so its other tags there stay; dropped in "No priority", all the group's tags come off), with a toast to undo it. Its order comes from `position`, an optional number on the card: one never dragged sits by when it was written, so new cards come last, and a dropped card goes halfway between its new neighbours, or, when they're too close for that, the column is spaced out again. History says "Moved on the board", and Cmd+Z undoes a move. A one-choice group with a tag named Done keeps that column and todos' boxes in step (added 2026-11-16, `doneTagOf`, `statusForMove` and `tagsForStatus` in `board.ts`): a todo dropped in Done is ticked, and one dragged out of it is reopened, each with a toast to undo; a repeating todo dropped there moves on to its next date, as its box does, and stays in its column. The other way round, ticking a todo that's on such a board, from its box, its menu, its sheet or the batch bar, moves it to Done, and reopening one from Done takes it back to the group's first column, in the same change to undo. A todo with none of the group's tags is left untagged, so ticking a todo that's on no board changes nothing else, and notes, which have no box, just move. AI apps' `complete_todo` doesn't move it yet. Each column ends with Add a card, which writes an entry the way the journal box reads it (`[]` for a todo, `@fri`, `#tag`) with the column's tag and the journal's filter, and stays open for the next; on the board the journal box gives way to these.

In a note, `/` adds a heading, list, checklist, quote, code, divider, photo or link to another note.

An entry's text can hold checklists, like a Trello card's (added 2026-11-16): `/` Checklist, the ☐ button in the formatting row, or `[ ] ` at the start of a line makes one, and Enter adds the next item. Its items are ticked in the open entry, where a ticked one greys out; they can nest. A bubble shows them as ☐ and ☑ lines. Unlike a `[] ` line in the writing box, which makes a todo of its own, these stay inside the entry. Markdown writes them as GitHub's `- [ ] ` and `- [x] ` and reads them back the same way (a list of only those is a checklist), so AI apps and copied Markdown keep them; plain text and rich text copies show ☐ and ☑. The native app doesn't know them yet.

Words in an entry can be hidden (added 2026-11-17), like an answer, a spoiler or a password: picked and hidden with the formatting row's Hide button (a crossed-out eye) or Cmd+Shift+H, or typed as `||words||`, as chat apps write spoilers. They show as a patch of drifting dots in the text's colour (since 2026-11-18; blurred before, which still let the words' shapes be read), so only how long they are shows, in the bubble, in a note only read (view only, a vault shared to view, history, a public link), and a press shows them, without opening the entry; another press hides them again, and they're hidden again the next time the app opens. While writing, the words the cursor is in show, with a dashed underline, so they can be edited. A title made from a note's first line shows them as •••. Search still finds them, and copies keep them: Markdown as `||words||` (read back the same way, so AI apps keep them), plain and rich text as just the words. The mark is `hidden` (`src/ui/editor/hidden.ts`); the native app shows them as plain text for now.

A note or todo can have more than one page (since 2026-11-18; from 2026-11-17 it could have one more, its back), like a question on page 1, its answer on page 2 and an example on page 3. Pages are just numbered pages, one after another: until 2026-11-18 they were a card's front and the pages behind it, turned like a flashcard, with a flip icon, a dashed border and a PAGE 2 label, and the first tab called Front. In the open entry, the pages button in the bar (an open book) adds page 2; once there is one, a row over the text has a numbered tab for each page (1, 2, 3), + to add another after the last (not while a new one is still blank), and Take out page N on a page, with an undo; going to a later page slides its text in from the right, and back from the left. Each page has its own editor and undo. Its bubble then has ‹ and › down its left and right sides, each the full height of the bubble (shown on hover, and always but faint on a touch screen), that step to the previous or next page, round and round: from the last, › goes to the first, and from the first, ‹ to the last (since 2026-11-18; for a moment neither went past the ends), with room kept at the sides so they cover no text; its bottom row says which page it's on (1/3), and the page slides in from the side it came from (for a moment on 2026-11-18 the arrows sat by the 1/3 in the bottom row): what's in the bubble slides, while the arrows and the copy button stay put, so a quick second click still lands on the arrow (the whole bubble slid at first, taking the arrow out from under the pointer), without movement with reduced motion (`usePager` in `src/ui/pages/journal.tsx`); the page shown is kept while the app is open, and the title stays on every page. A blank page is skipped in the bubble, and blank pages at the end are taken off. It's the card's `pages` field, a list of documents like `content`, missing or null on most cards (`cardPages` in `src/domain/content.ts`); a card from before pages has a `back` instead, read as its only page and cleared the next time its pages are written, so nothing needs migrating. Search finds words on every page, links from them count as backlinks, history compares them under "Page 2:" and so on and calls a change to them "Edited a page", restoring a version puts its pages back, and Discard puts them back too. Copies carry them after the first (Markdown under `## Page 2`, plain text after "Page 2:", rich text after a bold Page 2), and entries pasted back into the journal keep them (a back copied before there were pages comes in as page 2); the Markdown export, AI apps (reading a card) and public links show them after the first too. AI apps can't write pages yet, and the native app doesn't show them.

Due-date reminders (added 2026-11-17, once on the Later list) are notifications pushed by the server when an open todo comes due, shown even with the app closed. They're turned on for each browser under Settings, Reminders: Turn on reminders asks the browser's permission and leaves a push subscription on the server with the browser's time zone and language, and two choices kept with it: how long before a todo's time it reminds (at the time, or 5 minutes to 2 hours before) and when a todo with only a date reminds (9:00 unless changed). Send a test pushes one to every browser of the account; Turn off takes it away. As cards are pushed, by the app or by AI apps, the server notes each open todo with a due date that isn't waiting, archived or a template (a `reminders` table); every five minutes (a second cron in wrangler.jsonc) it sends what has come due and not been sent to the browsers of the vault's owners and editors, not its viewers: the todo's name, "Due at 3:00 PM" or "Due today", opening the todo when pressed. Each reminds once per browser for each due date, so moving a todo's date reminds again, a reminder more than six hours late isn't sent, and a browser the push service says is gone is forgotten. Todos in an encrypted vault have none: the server can't read them. The push is sent by the Worker itself with WebCrypto (`server/webpush.ts`: VAPID per RFC 8292, the message encrypted per RFC 8291, checked against the RFC's worked example), and shown by a few lines added to the service worker (`public/push-sw.js`), so it works in the installed app or a build, not the dev server. On iPhone and iPad, Safari only allows it for the app added to the Home Screen. The server's VAPID key pair is made by its owner (`node scripts/vapid-keys.mjs`, which only prints it) and set as `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY`; until then the Reminders section says reminders aren't set up. The native app has none yet.

Templates (added 2026-11-17) are notes and todos kept to start new ones from, like a packing list or a weekly review. They live in the journal, under the Templates chip in the title bar's filter row (`/journal?template=1`, and Templates in Cmd+K; the sidebar has no link of its own for them): the journal swaps to them, titled Templates, and the other filters, tags, vaults, boards, selection and menus work on them as on any entry; what's written in the box there is made a template. (Until later the same day they had a page of their own, with New template and a copy-making Save as template; `/templates` now leads to the filter.) Save as template, in an entry's menu or its sheet's bar, saves a copy of it under Templates and leaves the entry as it is, where it is, with an undo and Show in its toast (since 2026-11-18): the copy has its words, pages, tags, color and previews, and a todo's copy is an open todo with no dates. Until then the entry itself became a template, leaving the journal, with a Template switch (ticked on one, and back again from it), which read like a label and lost the entry from the journal; a todo keeps its dates, which a template doesn't pass on. A template's bubble has Use in its bottom row, and its menu Use this template, its sheet a note that it's a template with Use it, and Cmd+K "New from template: …": each starts a new entry from it in a sheet ready to type: its title, text, back, tags, color and previews come along, every checklist item unticked, and `{date}` (or `{today}`) in the title or text written as the day it's used ("Weekly review, Tuesday, November 17, 2026"). Discard in that sheet trashes it again, even before it's changed. A template is an entry with `template` set (`src/domain/templates.ts`): it syncs, shares and keeps a history like any entry ("Made a template"), and it's left out of the rest of the journal, the todo counts, reminders, the calendar, the timeline and stacks, though search still finds it. The Markdown export marks it `template: true`, and AI apps see that it's a template.

Entries can be grouped into a stack (added 2026-11-17), like a deck of cards, in an order of their own: pick two or more in the journal and press Stack (the layered icon) in the batch bar, and a new stack is made, saved at the time of stacking, so it shows in the journal now, today, opened to show them (until 2026-11-19 it took the first entry's time, landing back among older entries where it was easy to lose); pick a stack with them and they go in at its end instead. In the journal, a stack is one bubble, its cards fanned out behind it, with its name (its title, or with none the first line of its text, which then isn't shown again under it; "Stack" only when it has neither, and until 2026-11-19 whenever it had no title), its own text, the first three of its entries and "and N more"; "3 cards" in its bottom row opens it to show them all under it, along a line, each as in the stream, and closes it again (kept while the app is open). In an open stack each entry shows its photos and link previews under it, as in the stream (since 2026-11-19; it showed only the bubble before). The entries are dragged up and down to set their order (a mouse from anywhere on one, a finger from the grip in the gutter, or the arrow keys on the grip): a copy of its bubble (no wider than the bubble) follows the pointer while the card itself moves among the others to where it would land, faded, and it stays there when dropped, before the change is saved, so nothing jumps back for a moment. Take out of the stack, in an entry's menu (and a button in its sheet's bar, for phones), puts one back into the stream, with an undo. (Until 2026-11-18 a dashed gap showed where it would land, the copy fell to the bottom of the page instead of following the pointer, and an × under the grip took it out.) Its sheet lists them in order, each opening its own. An entry is in one stack at a time, and stacking it again takes it out of the one it was in; a stack doesn't go in a stack. Its entries fold into it wherever it shows, and show on their own where it doesn't: a filter that leaves the stack out (Todos, a tag only they have), and the board, where the stack is a card of its own. It's a note with a `stack` list of its entries' IDs (`src/domain/stacks.ts`), so it syncs, shares and keeps a history like any note ("Changed the stack", and restoring a version brings back its order); an entry that's trashed, archived or not on this device is left out of it but keeps its place, and comes back to it. Moving the stack to the Trash lets its entries go back into the stream. AI apps reading a stack get its entries in order, and the Markdown export lists them as links. The native app shows a stack as a plain note.

A bubble's bottom row shows what the entry holds at a glance, as a Trello card does, in the list and on the board: its checklist progress (☑ 2/5, tinted green when every item is ticked) and how many of its comments are still open. Comments live on the server, so the counts come with each sync, in the `comments` list `/api/shared` now returns (open comments on every card the account can see, through its vault or a share), are kept on the device, and are asked for again straight after a comment is written, resolved or deleted. A photo needs no cover of its own: an entry's photos already show under its card, as the photo setting says.

Cmd+K (Ctrl+K elsewhere), or `/` anywhere outside a text box, opens a command box for doing anything from the keyboard: every filter, sort and page, new notes, locking vaults, finding notes by their text, and saving what's typed straight to the journal with the same markers. Starting with `/` lists only commands.

Outside text boxes, the journal takes keys for entries: Cmd+A selects all shown, Cmd+C copies the selected entries (or the one focused from the keyboard), Cmd+X cuts them, Delete moves them to the Trash, and Cmd+Z undoes the last change, anywhere in the app, with Shift to redo (see the notes on undo and redo). Up and down arrows move between entries, picking with Shift, and Home and End go to the first and the last; with nothing focused (as after a click on empty space), Space, ↓ and ↑ go into the entries instead of scrolling the page, from the one in the middle of the screen: Space focuses that one (a second Space then picks it), and ↓ or ↑ the one after or before it (`focusStream`, since 2026-11-18; for a moment ↓ and ↑ went to the first or last on the screen), so the journal can be read from the keyboard without tabbing in first. An entry reached from the keyboard is scrolled into the part of the page nothing covers, under the title bar and its pinned day badge and above the writing box (`revealBubble`; until 2026-11-18 it could stop under the writing box), and shows its hover buttons and page arrows while focused. ← and → on a focused entry step through its pages, round and round like the arrows. Escape leaves the focused entry (while picking, the first Escape stops picking and a second leaves it), and then the one left counts as the middle, if it's still on the screen: Space comes back to it, ↓ goes on to the next and ↑ to the one before. Cmd+V pastes copied entries as new ones, written now, into whatever the journal is narrowed to; anything else pasted goes into the writing box. Copying puts text for other apps on the clipboard plus an exact copy in the app's own type, so pasted back into the journal, formatting, photos, tags, due dates, times and repeats survive. `?` lists every shortcut. A copy button in each bubble's top right corner (on hover, in room the bubble keeps for it so it covers no text), Copy in the menu of several picked entries and the copy button in its sheet's bar copy that one entry the same way. If the browser refuses the copy, the toast says so. A bubble focused by a click never counts as focused for Delete, so a stray key can't trash it.

What other apps get comes in three styles, picked for each copy and paste (added 2026-11-16). Copy & paste in Settings, kept on each device (`src/ui/clipboardPrefs.ts`), sets the style each one starts in, and a small chip by what was copied or pasted offers the others for that one, as word processors do (since 2026-11-19; until then it was a toast, "Pasted with formatting" or "Copied 2 entries as rich text" with a button for each other style, that sat over the bottom of the page). The chip is a clipboard (a copy icon for a copy) and an arrow; pressed, it opens to the styles, the one used ticked, and another copies the same thing again that way or puts the paste back that way (`choiceChip` in `src/ui/clipboardChoice.ts`). After a paste, or words copied or cut in an editor (an open entry, the writing box, a read-only view), it sits right after the text, or where cut words were (`ClipboardChoices` in `src/ui/editor/clipboardChoices.ts`), and goes when anything is typed, the cursor leaves the text, or on Escape, so a paste is always as it left it while the chip shows; a copy's also goes after 10 seconds unless opened. Entries copied (the bubble's copy button, its menu, Cmd+C) get it beside the first of them on the screen, level with its top where the copy button is, or inside that corner where there's no room beside it, and from the batch bar or the sheet's bar under or over the button pressed (`showChoiceNear`); it follows the page as it scrolls and goes after 10 seconds unless opened or pointed at, on a press anywhere else, or on Escape. With nowhere to show it (an entry copied that isn't on the screen), it's the toast as before. A paste that would come out the same in every style, plain words, offers nothing. Copy as: Rich text (the default) puts HTML on the clipboard for apps that show formatting, with each entry's words as plain text for apps that don't (its title, then its body with lines and list markers kept and links as their addresses; in the HTML a todo starts with ☐ or ☑ and photos are left out, `src/domain/html.ts`); Markdown is the way the journal box reads it, todos as `[ ] Title @date @time @repeat #tag` and notes as Markdown with their tags on a last line; Plain text is the words alone. Words picked in an open entry, the writing box or a read-only view copy and cut the same way (`src/ui/editor/clipboardStyle.ts`): Rich text is the editor's own HTML with those plain words beside it; Markdown or plain text go with no HTML, and a pick inside one list item or quote is just its words; text inside a code block is always copied as it is. Paste as: Keep formatting (the default) is the editor's own paste; Markdown reads pasted text as Markdown (`fromMarkdown`, the one AI apps write through), so `**bold**`, headings, lists and `[[Title]]` links to cards (in an open entry; the writing box keeps them as written) become formatting; Plain text drops the formatting, a paragraph to a line. ### Labels are notes
A label is a card of type `tag`, with its own description and links. Tagging a note is a typed link to the tag card, so the tag card's backlinks list every tagged note.

### No folders
There is no separate folder or collection concept. A folder is a tag card pinned in the sidebar. A note can carry many tags, so it can sit in several "folders" at once.

### Vaults
A vault answers "who can see this". Topics belong in tags, not vaults.

- Each card has exactly one home vault, where it lives: it's stored and encrypted there, and moving it changes it. It can also be in other vaults (decided 2026-11-15): that's a share with everyone in the vault, so its members see it there and get no more than the vault gives them (a viewer can comment at most). A card isn't stored twice, which keeps one copy, one key and one history.
- A vault named after a group (e.g. "High school") only makes sense if those people are members, or it needs its own PIN.
- Set per vault: lock (none or PIN), AI access (off, read, read + write), members.
- When locked: left out of UI, search, backlinks and the journal. Links to its notes show as "Locked". A vault can be fully hidden until unlocked.
- Auto-lock on timeout or when the app goes to the background.
- Search covers only unlocked vaults.

### Unlock
Each private vault has its own PIN or password, separate from the phone's screen lock.

Fingerprint unlock is opt-in and off by default, with a warning: the device accepts any enrolled fingerprint, and family members often have theirs enrolled.

### Sharing a single note
A card has a home vault plus extra share grants.

Flow: pressing Share on a note in Family and picking High school warns "This note is in Family (4 people). Share with High school (23 people)?", then asks for View / Comment / Edit, or Anyone with the link. "Anyone with the link" is what the owner means by "global": an unlisted URL, read-only, with optional expiry and revocable. It is not listed or indexed anywhere.

Rules:
- Sharing a note does not share the notes it links to. Those show as "Not shared".
- A recipient only sees backlinks from notes they can access.
- Sharing from a private vault requires the vault PIN and an extra confirmation.

### MCP server (so Claude and other AI subscriptions can access data)
Runs beside the sync server on the same database, using Cloudflare's MCP setup for Workers and its OAuth library.

- Per-vault AI access: off (default), read, read + write. Private vaults can never have AI access.
- The server enforces this, not the AI.
- Write access is approved by the owner, once per vault (decided 2026-11-10): the AI access setting is the approval, with no per-change prompts. Every AI edit can be undone from history.
- Tools, read: `search_cards` (by type and vault), `get_card` (with backlinks), `list_todos(due, status)`.
- Tools, write: `create_note`, `add_todo` (with a time and repeat), `complete_todo`, plus editing existing notes.
- Every AI edit creates a version labeled as AI-authored, undoable in one click.
- Notes shared with you by others are read-only to the AI, because they could contain text written to manipulate it.

### Encryption: later, but design for it now
- The server only stores opaque records. Plain fields: `id, vault_id, updated_at, deleted, seq`. Everything else goes in one `payload` field: JSON now, ciphertext later, with no server change.
- Search index and backlinks are derived on each device and never synced. (Exception: open vaults with AI access can be searched server-side, e.g. D1 FTS5, for MCP.)
- Later crypto: password through Argon2id to a key-encryption key, which wraps a random AES-GCM key per vault. Each card gets its own key wrapped by the vault key, so sharing one note means sharing only that note's key. Public links keep the key in the URL `#` fragment. Print a one-time recovery key.
- Open vaults: server-side encryption at rest. Private vaults: end-to-end.

Private vaults are end-to-end encrypted since Milestone 7. Open vaults are still readable by someone tech-savvy with the unlocked laptop, which is accepted for this threat model.

## Technical decisions

- **Client:** PWA first. React, TypeScript, Vite, vite-plugin-pwa, React Router, Dexie (IndexedDB), TipTap editor with `[[link]]` autocomplete, MiniSearch, fflate for zip export.
- **Colors:** a few tokens at the top of `src/ui/styles.css`, light and dark: the page, cards on it, wells (chips, switches), what's raised out of a well (a switch's pick), lines, text, muted text and the accent. Refined 2026-11-17 so neighbours are easy to tell apart, chips from the page, a switch's pick from its well, a chip in use from one that isn't, especially in dark mode, and muted text keeps 4.5:1 contrast.
- Keep storage and crypto behind small interfaces. (Meant at first for wrapping the web UI in Tauri 2; the native apps reimplement both instead, see the native apps notes.)
- Call `navigator.storage.persist()`. Build export/backup early, including Markdown plus image files.
- **Note format:** TipTap JSON stored in the card, plus Markdown export. Links by card ID survive renames, and it supports comments and live co-editing through Yjs.
- **Sync server:** hosted, not on the Mac mini. Hono with D1, running as a Cloudflare Worker that also serves the app's files (on the site's own address, so sessions can use a secure cookie). `POST /api/sync/push` assigns an increasing `seq`; `GET /api/sync/pull?since=<seq>`. Conflict: newest version per card wins, the loser is kept as a conflict copy. Once a day (a Cron Trigger) the Worker deletes expired sessions, sign-in, pairing and Drive codes, and AI app grants whose refresh token ran out. Avoid sync engines that need to read the data (PowerSync, Dexie Cloud); avoid Supabase free tier, which pauses when inactive.
- **Auth:** Google sign-in. Single user at first, but multi-user in the data model from day one; every request checks vault membership.
- **Photos:** stored in Google Drive, behind a storage interface, with cards referencing their own attachment ID. Offline photos queue on the device and upload later, with small previews cached locally.
  - Uses the `drive.file` scope; the Worker does the one-time OAuth login and holds the refresh token, handing the app short-lived tokens so the phone isn't re-prompted hourly.
  - Known consequences, to handle at Milestones 5 and 6:
    - Photos from private vaults sit in the owner's Drive, where anyone who can open their Drive app could see them until encryption ships.
    - Shared vaults need a way for members to read the owner's photos (Drive permissions per person, or the Worker serving them with the owner's token).
  - Cloudflare R2 was considered (10 GB free, no download fees, simpler for shared vaults). The storage interface keeps it possible as a later backend.

## Implementation notes from Milestone 3

- A PIN is stored as a salted PBKDF2 verifier and syncs with the vault, so one PIN works on every device. It gates the app and is not encryption, so it doesn't protect against someone reading browser storage or the server's database until Milestone 7.
- Open vaults are held in memory only. They lock when the app goes to the background, after five idle minutes, and on reload. After five wrong PINs, attempts wait 30 seconds.
- A PIN is typed into a plain text box whose own letters are invisible, with dots drawn over them (`src/ui/PinInput.tsx`, since 2026-11-19), and marked for password managers to ignore. On a Mac, typing in a password box, or in a text box masked with `-webkit-text-security` (as the PIN box was from 2026-11-13), makes Chrome turn on Secure Input, and Chrome kept it on after unlocking took the box away. While it's on, mouse tools such as Logi Options and Karabiner-Elements can't pass the scroll wheel on, so nothing scrolled in any app until Chrome was left and come back to. Found by logging which app held Secure Input (`ioreg -l -w 0 | grep SecureInput`) while unlocking; the 2026-11-13 fix had blamed a password manager's popup instead, and a 2026-11-19 fix that took focus off the box before unlocking didn't help.
- Locked cards are removed where the index is built, so lists, search, backlinks, Today, Calendar and Markdown export can't reach them. Links into a locked vault read "Locked", and a JSON backup leaves locked vaults out.
- Each account's default vault can't be locked, because new cards go there.
- A hidden vault is unlocked by entering its PIN under Vaults, and its name is not shown until then.
- Fingerprint unlock is per device and off by default. It uses the device's built-in authenticator through WebAuthn, and has not been tried on a real phone.
- A forgotten PIN can't be recovered yet. Vault creation and PIN changes need a connection.

## Implementation notes from version history

- The server keeps history, so every device sees the same versions and a new device gets them too. It needs a connection; offline, the page says so.
- One version covers a stretch of edits by one person on one device: saves within 10 minutes of each other extend it, up to an hour. Both sides of a sync conflict are kept as separate versions. At most 200 versions per card.
- A version records the device it came from (decided 2026-11-13): an ID the device makes up for itself and a name like "Chrome on Mac", sent with each push. It also records whether the card was in the Trash, so moving a card to the Trash, or back, is a version of its own.
- `GET /api/versions` lists the newest versions of every card the user can read, each with the version it replaced, 40 to a page. It is what the History page shows of other devices, other people and AI apps. Only the user's own versions say which device.
- A card that existed before history was kept gets its earlier state saved, with no author, the first time it changes.
- History is visible to members of the card's current vault. Locked cards show the unlock panel instead, as their card page does.
- The page compares a version with the one before it, word by word (each CJK character counts as a word), or shows its full text. A line that was mostly rewritten is shown as the old line and the new one.
- Restore writes the old title, text, tags and todo fields back as a new change, so it can itself be undone. It seals the newest version first, so the restore always gets its own entry.
- Edits on this device that haven't synced yet appear as their own entry at the top.
- Undo in the editor covers this device's typing only. A change arriving from sync is not undoable, so undo can't revert another device's edit. Older states are restored from history.

## Implementation notes from undo and redo

- Each device keeps a log of the changes it made to cards (decided 2026-11-13): the card before and after, the fields that changed, and the action the change was part of. The newest 500 are kept, in the device's database. It holds this device's changes only. Changes by other devices, other people and AI apps arrive by sync and aren't in it; the server's history has those, and the History page shows them from there.
- Cmd+Z (Ctrl+Z) outside a text box undoes the last action, and Cmd+Shift+Z (Ctrl+Shift+Z, or Ctrl+Y) redoes it. Both are in the command box too. Each says what it did in a toast that offers the way back. A text box keeps its own undo for what is typed in it.
- An action is everything one click did: trashing five picked entries, or pasting three, is undone together. Typing is one change per card for a stretch of saves: saves within 5 minutes of each other join, for up to 30 minutes, so undo from outside the editor takes back the whole stretch.
- Undo is checked against what the card holds now. A change can be undone only while every field it set is still as it left it, and undoing puts back those fields alone. So an edit made since, here or on another device, is never overwritten, and other fields changed since stay as they are. A change that can't be undone is passed over for the one before it.
- Undoing a new entry moves it to the Trash, and redo brings it back. A blank card isn't logged until something is in it.
- Undone changes stay in the log, marked, until they're redone, so redo works after a reload. As in any editor, keyboard redo stops once something else has changed after the undo.
- The log stores cards the way their vault does, so changes in an encrypted vault are encrypted in it, and can't be undone while the vault is locked. Moving a card into an encrypted vault drops its earlier, readable changes from the log and keeps the move's own "before" under the new vault's key. So does encrypting a vault.
- Undo needs the same access as the change: a viewer can't, and undoing a move needs write access to the vault the card goes back to.
- Undo in a toast (ticking a todo, Trash, a move, a batch change, paste, turning a note into a todo, restoring a version) takes back that action from the log, so it follows the same rules.
- Restoring a backup, changes from sync and conflict copies aren't logged. History still shows what this device restored or copied, from the server's versions: a version from this device is left to the log only when the log has that card changing at that time (counting undo and redo).
- History, in the sidebar and the command box, is the log as a page (`/history`): each action newest first, grouped by day, with what it did, the entry, the time, the lines it changed on request, and Undo or Redo for that change alone. An action that changed several entries is shown together, with Undo all. A change whose entry was changed again later says so, and offers no button until the later change comes off.
- The history takes the journal's filters (decided 2026-11-13). On the History page the sidebar's filters stay on it: open todos, one tag, one vault, a day. A change is shown when its entry passed the filter before the change or after it, so "Done" shows the ticking and "Open" shows it too. Journal and History switch between the two views and keep the filter.
- On a filtered history, Cmd+Z, the command box and the page's undo and redo buttons keep to the changes shown, so the last change to a tag's entries can be undone without touching anything else. Everywhere else they act on the whole log.
- Changes in a locked vault are listed as "Locked entry" with no button, and only under that vault or with no filter; a hidden vault's changes aren't listed until it's unlocked. That holds for a locked vault that isn't encrypted too, though the log could read its cards, and for a change that moved a card out of a locked vault.
- History also shows what was changed elsewhere (decided 2026-11-13): on the user's other devices, by AI apps, and by other people in shared vaults and on shared cards. These come from the server's versions of every card, each read as a change from the version before it, and sit among this device's changes by time. Each says who or what made it: the device ("Safari on iPhone"), the AI app, or the person. Each links to the entry's version history.
- This device's own changes are shown from its log, not from the server, so nothing is listed twice and undo and redo work as before. Its changes from before the log begins (the log keeps 500, and a new browser starts with none) are shown from the server.
- The page loads the newest 40 versions and asks again after a sync, at most every 20 seconds, so a change made elsewhere shows up by itself. "Show older changes" loads the next 40. A history that shows fewer than 15 actions, as under a narrow filter, loads up to three more pages by itself. This device's older changes are held back until the server's of the same time are loaded, so the list has no gaps.
- History needs a connection for what was changed elsewhere. Offline, after 3 seconds, it shows this device's changes and says the others may be missing.
- Changes from elsewhere follow the locked-vault rules above: "Locked entry" while their vault is locked, nothing for a hidden vault.
- A change from elsewhere has Undo too, under the same rule as any other: only while the entry still holds what the change left, and with the same access. Undoing it is a change made on this device: it joins the log, syncs, and can be undone itself, which is the way back the toast offers. There is no Redo on the row. The page's undo button and Cmd+Z stay with this device's changes.
- Limits of what is shown from elsewhere. Saves close together on one device are one version, so several quick changes there show as one. Moving a card to another vault isn't a version, so a move made elsewhere isn't listed. A device that was offline has its changes listed at the time they were made, so they can turn up below newer ones. Versions saved before devices signed their saves say "One of your devices", and so do the Swift app's, which doesn't sign its saves yet.

- The MCP `instructions` tell the model to treat card text as data, not instructions.

## Implementation notes from Milestone 5

- A photo is a block node in the card body holding an attachment ID. The image itself is never in the card payload.
- Photos are shrunk on the device (long edge 2048 px, JPEG at 85%; small GIF, PNG and WebP keep their format), saved in IndexedDB, and shown from there at once. An upload queue sends them when online, so photos work offline.
- Pasting a picture (2026-11-19): a file on the clipboard is added as before, but a picture copied from a web page, or from an app that copies it the same way, often comes as just `<img src>` in HTML with no file, and was lost (the editor has no `<img>`, so nothing went in while the toast said "Pasted with formatting"). `picturesInHtml` (`src/photos/pasted.ts`) finds the addresses: HTML that's only pictures adds them as photos; pictures among words follow the pasted words when the paste keeps formatting. A `data:` picture is read on the device; a web one is fetched by the server, `POST /api/fetch-image {url}` (`imageRoutes` in `server/unfurl.ts`), since most sites don't let a page fetch their pictures. It goes through the link preview's checks (public addresses only, each redirect checked), keeps only pictures the device can shrink (not SVG) up to 10 MB, and says what went wrong in a sentence the toast shows. An added photo no longer stays picked, which let the next key or paste replace it: the cursor goes to the line after it (a new one when none follows), several go in one after another, and one added at the start of a line goes before the line instead of splitting it. When the server can't take photos (`not_configured`, or `needs_drive` with a Settings button), a toast says the photo stays on this device, since before only Settings said so. Until 2026-11-19 the live site had no `GOOGLE_CLIENT_SECRET`, so every photo there stayed on the device it was added on; photos waiting like that upload once Drive is connected.
- The server does every Drive call, holding the owner's refresh token. Devices never get Google tokens. Members of a shared vault see photos through the server, which reads them from the owner's Drive.
- Drive access is `drive.file`, so the app sees only files it made, in a "Notes app photos" folder. Google's redirect back carries a one-time state, because the SameSite=Strict session cookie isn't sent on it.
- A photo is checked against the vault it was added in. Moving a card to another vault doesn't move its photos' access yet; members of the new vault won't see them. Handle this with sharing.
- Deleting a photo from a note leaves the file in Drive. A clean-up for unreferenced photos can come later.
- Markdown export writes `![alt](attachment:id)`, but doesn't put the image files in the zip yet.
- Files (2026-11-19): any other kind of file is attached as it is, as a `file` block (`FileBlock`, `src/ui/editor/file.tsx`) keeping its attachment ID and the name, type and size it was added with, so it shows without being fetched (`fileAttachments` reads them). It goes the photos' way: saved on the device (`PhotoService.addFile`, the record marked `file: { name }`, nothing shrunk), uploaded in the background with `kind=file&name=` to the same `PUT /api/attachments/:id`, into the same Drive folder named `<id> <name>`, up to 25 MB (`MAX_FILE_BYTES`, against a photo's 10 MB; Google documents the multipart upload used here for 5 MB or less, and nothing bigger has been tried against Drive yet; if Drive turns one down, it stays on the device and is retried rather than lost, and a resumable upload would be the fix). The paperclip in the writing box and in an entry's toolbar, and `/file`, pick files; a pasted or dropped file that isn't a picture (or is an SVG) becomes a file block. Under a bubble a file is a chip (`FileChip`, `src/ui/files.tsx`): pressing it opens a PDF, a picture, plain text, sound or video in a new tab, and downloads any other kind under its name; its arrow always downloads. Since a file is shown from a `blob:` address on the app's own origin, only those kinds open, and only as the type its block names, so an attached web page can never run as the app; everything else goes out as `application/octet-stream`. The server likewise sends anything that isn't a photo with `content-disposition: attachment`, `content-security-policy: sandbox` and `nosniff` (`attachmentHeaders`), to members and on a public link (`/api/public/:token/files/:id`, only a file the card holds; the public page shows it as a link that downloads). Contains has With files. Markdown writes a file as `[name](attachment:id)` and reads it back, without its type or size. Settings calls its section Photos and files. The demo has a PDF, a CSV and a text file (`scripts/demoFiles`, written by `make.mjs`, served by the dev server for `demo-file-<name>` like the demo's photos).

## Implementation notes from Milestone 6

- Sharing a vault: its owner adds people by email as editors or viewers. Someone without an account is invited and joins at first sign-in. Members can leave. Viewers can read and comment; editors can also change, add, move and trash cards.
- Private vaults can't be shared, and a shared vault can't get a PIN, since every member would need it. Sharing private vaults with their own key is a Milestone 7 question.
- Sharing one card: with a person by email, or with everyone in another vault the sharer belongs to, for viewing, commenting or editing. Edit access changes content only; recipients can't move, trash or re-create the card. Only members who can edit the card's own vault can share it onward. The share dialog lists each person, invite and vault the card is shared with, and each one's access can be changed there or removed; a vault the sharer isn't in, shared by someone else, only shows its access. A card shared with a vault shows in that vault's journal for everyone in it, the sharer too, while still living in its own vault: `/shared` lists which cards are shared into which of the account's vaults (`vaults`, next to `cards`), and the journal's vault filter takes those in. Sharing or unsharing syncs at once, so it shows there straight away.
- Sharing a card into another vault shows a warning naming both vaults and how many people are in each. Sharing from a private vault needs the vault open and a confirmation.
- Public links: unlisted, read only, optional expiry (1, 7 or 30 days), revocable, at `/s/<token>`. The server strips linked cards' stored titles from the public response, and serves only photos the card contains. Cards in an encrypted vault can't be shared yet (the key would have to move into the URL fragment): encrypting a vault, or moving a card into an encrypted one, ends that card's shares, waiting invites and public links.
- Recipients sync shared cards like their own. When access grows the device pulls from the start, since a newly shared card can be older than its cursor; when access ends, those cards are removed from the device.
- Links to cards the account can't see read "Not shared" everywhere, rather than the title stored when the link was made.
- Comments are server-only, so they need a connection. They show under a card once others can see it, or once it has comments.
- Drafts (added 2026-11-19, synced the same day): what's written but not yet sent is kept as it's typed and follows the account between devices, as Telegram's drafts do: the journal box's, one for each view of the journal (its path without the sort, the same key the box is made new by), and a comment's, one for each entry. `Drafts` (`src/state/drafts.ts`, one per account, on `useCards`) keeps each in `localStorage` at once, so a reload or closing the app loses nothing, sends the changed ones a second after typing stops (and as the app is hidden), and after each sync fetches those changed since it last asked (`GET /api/drafts?since=`, from a minute before, in case the server's clocks disagree). The server (`server/drafts.ts`, migration 0015) keeps one row per account, box and key, and the last to arrive wins; a draft changed here and not yet sent wins over one fetched, and is sent at the next sync when offline. An open box takes one fetched from another device unless something is being written in it. One sent or emptied is sent as null and kept as a NULL row, so other devices drop theirs too; the daily cleanup removes rows 30 days old, and the device forgets its own after 30 days or at sign-out. A journal draft bound for an encrypted vault (the view's vault, or `#diary` typed in it, when that vault has a PIN) is kept only in memory while the app is open, never stored or sent, and any copy sent before is taken back off the server, since those entries are only ever on their members' devices; the words typed before `#diary` may have gone up in the second before it was typed, as the box can't know yet. Comment drafts are sent like any, as the comment itself goes to the server in the clear. Decided: a draft per view rather than one for the whole journal, so text written into a vault or tag view isn't saved into another by mistake; and no merging of two devices' edits to one draft, as a chat app does none. The demo leaves two, as if from another device: in the journal box when it shows #travel, and a reply to Sam's open question under the Kyoto trip.
- Scroll rail (added 2026-11-19): a rail down the right of every page that scrolls through all of its entries or what they hold, as Google Photos has: the journal's stream in every sort (and so the Archive, Templates and the Trash), Photos, Links and Files. `ScrollRail` (`src/ui/ScrollRail.tsx`) takes each item's key in page order (its day, or a tag group's tag, or none for no due date) and finds items by `data-rail-at`; `src/domain/rail.ts` picks the marks (years with a dot per month across years, months within a year, else the groups' names, spaced so labels don't overlap) and does the arithmetic: each item has an equal share of the rail, and the line the page is read at runs from the top of the view to its foot as the page scrolls from top to end, so the thumb is at an end exactly when the page is, and a jump scrolls by that same rule turned round. With a mouse on a wide screen it's always there, in place of the hidden scroll bar, labelled, with the month or day pointed at in a bubble; on a touch screen or a narrow one only a handle shows, while the page scrolls, and the marks while it's held; the rail ends above the button that jumps to the newest entries, so the handle never covers it. Since the stream draws 150 entries at a time, it now draws a stretch: a jump far off draws 150 around where it lands (`stretchFor`), with buttons that load more above and below (asked again once a jump settles, as one already in range when the page lands is never heard of otherwise), and going to the end (the jump button, or saving from the box) draws the end again (`toEnd`). Decided: equal shares per item rather than per pixel, as the stream doesn't lay out what it hasn't drawn; Changes and Search are left without one, as they aren't entries in date order. The demo has eight entries going back three years, three with new photos, so the rail shows years.
- Reactions (added 2026-11-18) are emoji on an entry, as on a chat message: a smiley at the start of its bubble's bottom row (after its reactions once it has some), shown on hover, and one under its tags in its sheet, where a phone reaches it, open a picker with the common six (👍 ❤️ 😂 🎉 🔥 👀) first and More for any emoji: a list by group with words to search by (`src/ui/emojiData.ts`), Recent ones on this device at the top, and anything typed or pasted in, from the system's emoji keyboard, so no emoji is out of reach without shipping all of Unicode's. Each shows on the left of the bubble's bottom row with its count, pressed (tinted) where this account's is on, and a press puts yours on or takes it off; its tooltip says who, as "You and 2 others". Unlike comments, they're part of the entry (`reactions`: each emoji with the account IDs on it, `src/domain/reactions.ts`), so they work offline, sync with it, are encrypted with it in a private vault and show in its history as "Changed reactions". So whoever can change the entry can react, even while it's set to view only, since a reaction leaves its words alone; a viewer sees them but can't add one, which a server-side table like comments' would allow, at the cost of working offline. Two people reacting to the same entry at the same moment is a conflict like any other edit, and the later wins.
- AI apps treat shared vaults as read only (Milestone 4), so text written by other people can't steer AI edits.
- Not done yet: notifications when something is shared, and moving a card's photos' access along with the card.

## Implementation notes from Milestone 7

- Each private vault has a random AES-256-GCM key, stored only wrapped: by a key derived from the PIN with Argon2id (19 MiB, 2 passes, via hash-wasm 4.12.0), and by a recovery key shown once. The server and devices never store the vault key unwrapped.
- A card in an encrypted vault is encrypted on the device as it is written, bound to its ID and vault. IndexedDB, the server, version history and conflict copies hold only ciphertext (`e1:` payloads). The server refuses plaintext into an encrypted vault.
- Unlocking unwraps the key, which also checks the PIN. Keys live in memory only and are forgotten when the vault locks. Fingerprint unlock keeps a non-extractable copy of the key on that device.
- Edits to encrypted cards skip the plaintext crash journal. A crash mid-save can lose the last few hundred milliseconds of typing in a private vault, rather than leave it readable.
- New private vaults are encrypted from the start. A private vault from before Milestone 7 shows "Encrypt this vault"; doing so re-stores every card encrypted and purges the plaintext versions from the server's history.
- Forgot PIN: the recovery key opens the vault and sets a new PIN. Changing the PIN rewraps the same key. Removing the PIN decrypts the vault.
- The PIN is the weak point: anyone with a copy of the server database can try PINs offline, so a 4-digit PIN falls in under an hour. A longer passphrase is much stronger. Worth a warning in the app later.
- Not covered yet: photos in private vaults are not encrypted in Drive or on the device; cards in encrypted vaults can't be shared or published (they need per-card keys, with the key in the link's `#` fragment); open vaults rely on Cloudflare's encryption at rest rather than their own key.

Nearing the end of what's drawn, or pressing "Show earlier entries", draws 150 more, keeping the screen where it was. With 3,000 entries, drawing them all made ticking one todo take over a second in the dev build; drawing 150 takes about a tenth of that. Select all, ranges and batch changes still cover every entry the filter shows.

The repository works out where the words go when the switch lands (`src/domain/retype.ts`), after any edit still on its way, and the editor saves when it loses focus, so words typed just before the click move too. The markers are read when the box is saved (`src/domain/entry.ts`), and `#todo` and `#diary` never become tags.

A todo is overdue once its day has passed, or on its day once its time has. An overdue todo's due date shows in the alert color (red), in its bubble and in its sheet's bar; a done one's doesn't. One that fell behind skips to the first time after today, keeping its rhythm (a weekly todo due last Monday, ticked Wednesday, is next due Monday); one ticked early moves on from its due date. Months keep the day of the month, or the month's last day when it's shorter, counted from the due date so short months don't wear it down. Batch "Done" and the MCP `complete_todo` do the same; the MCP server counts today in UTC. Taking the date off takes the time and repeat with it. There are no reminders at the due time yet.
- The filter lives in the address (`/journal?type=todo&status=today&tag=…&vault=…&when=week&sort=due`), so the back button and bookmarks work. `when` is a preset (`today`, `week`, `month`), a day (`2026-11-12`) or a range of days (`2026-11-03..2026-11-09`, both ends included). Pick dates in the sidebar opens a calendar dialog: the first press picks a day, the next the other end of a range, and Show applies it; a dot marks days with entries, and the arrow keys move between days. The month's title opens that year's months, and the year's title a page of twelve years, each marked where there are entries, so a far month is a few presses away. Once a first day is picked, a line under the calendar measures a length from it, read as a sentence: a number (− and +, or typed), days, weeks, months or years, and starting, ending or either side of the day, as in "2 weeks ending Nov 9". Changing any part sets the range, both days included; until the side is chosen it starts on the day, or ends there when starting would run past today, and a press on another day then moves the day it's measured from; Escape steps back toward the days before it closes. A round button just above the writing box jumps back to where the newest entries are, the bottom in the oldest-first chat and the top in other orders, shown only once the page is well away from there. It goes straight there, without a scrolling animation, and so does the jump to a new entry after writing it (2026-11-17). Each day's badge in the journal stays pinned under the title bar while that day's entries scroll past, and (in the orders grouped by the day written) opens the same dialog at that day, so a press and Show picks it and another press makes a range from it; a day already picked opens the same way. Writing in the box backdates new entries only to a single picked day, not a range. `/today` and `/upcoming` redirect to their filters, and Calendar days open the journal for that day.
- A tag's own page (rename, describe, pin) is still at `/card/:id`, reached from the tag button at the top of a tag-filtered journal or from All tags.
- New entries take the filter's tag and vault; a todo filter makes the box write todos, and "Due today" makes them due today. A tag created from the box goes in the default vault.
- With the Diary vault locked (or any vault the entry would go into), the text stays in the box and the vault's PIN is asked for above it.
- The box is a small TipTap editor (`JournalBox`). On saving, `entriesFromDoc` reads its rich text: each checkbox is a todo and the blocks between them one note, with formatting, links and photos kept. Checkbox lists never end up inside a note, so the note editor needn't support them. Enter saves on a computer, Shift+Enter starts a new line (the next checkbox in a list), and Cmd+Enter saves anywhere.
- The command box still reads plain text (`parseEntries`). One text can hold several entries. A new tag typed in several of them is made once, and if part of the text can't be saved (the Diary vault is locked) none of it is. Cards made together get creation times a millisecond apart, so they keep the order they were typed in.
- Notes and todos open at `/journal/:id` in a sheet over the page they were opened from (Search, Calendar, a filtered journal), so the back button closes it. Old `/notes/:id` and `/card/:id` links to notes and todos redirect there. A click outside it closes it, and so does one outside the command palette, the photo viewer, the phone's tags-and-vaults sheet and the shortcuts list, but only when the press started outside too (`useBackdropClose`, since 2026-11-19): selecting text and letting go past the sheet's edge ends in a click on the backdrop, which used to close the sheet mid-edit. In the sheet's editor Shift+Enter and Cmd+Enter do what Enter does (`OneEnter`, since 2026-11-19): a new line, the next list item, a new line in code. TipTap's default made them a line break inside the paragraph, which looked different (paragraphs had a 0.7em gap, breaks none) and in a list added no item, a difference the journal box and the bubbles never showed. Lines of text in a card now follow each other with no gap, as in the bubble; an empty line makes one. Line breaks already saved, or brought in from Markdown, still show as they were.
- The box saves on Enter on a computer (Shift+Enter for a new line). On a phone, Return makes a new line and the send button saves.
- A batch change skips entries it doesn't apply to (a due date on a note) or that already match, and entries this account can't change, which the toast counts. Undo puts back each entry's own earlier value. Picks that fall outside a new filter are kept but not counted or changed.
- Translations where the browser can't make them come from `POST /api/translate {cardId, pieces, to, otherwise}`: the pieces a bubble shows (at most 60, 8,000 characters in all), translated into `to`, or into `otherwise` when they're in `to` already (a second call), else `{kind: 'same'}`. The entry has to be one the account can read and not in an encrypted vault (403), and each account gets 200 a day by UTC date, counted in `translation_counts` with one upsert that stops at the cap, so two at once can't both take the last one (429 past it; the daily cleanup drops past days). One call to `@cf/google/gemma-4-26b-a4b-it` on Workers AI, with its thinking off and its answer held to a JSON schema with exactly as many pieces as were sent, which also names the language they were in; an answer that doesn't fit is a 502, and the app offers Google instead. Without the `AI` binding the route answers 501. Workers AI's free daily allowance covers a person's use; past it, Cloudflare bills the account, or on the free plan the calls fail and Google is offered.
- Link previews come from `POST /api/unfurl {url}`: the server reads at most 256 KB of the page within 5 seconds, takes its Open Graph tags or `<title>`, and caches the result for a day. It fetches only public web addresses on ports 80 and 443, following up to three redirects itself and checking each one, so it can't be pointed at the server's own network. The address goes in the request body so it stays out of logs.
- The app keeps each preview on the device for a week (a page that gave nothing is asked again after an hour). Links in encrypted vaults are never previewed, so those addresses don't leave the device. A preview's image loads straight from the page's site, with no referrer.
- In the command box, text with markers (`[]`, `#tag`, `@friday`) offers saving first; other text lists matching commands, then matching notes, then saving. Commands whose name matches come before ones that match by keyword.
- The native apps still have the earlier layout; they follow once the web design settles.

### The diary is a vault

Decided 2026-11-14. A day used to have one diary card, with its own type, ID (`diary:<vault>:<date>`) and page, and `#diary` lines were added to it. Now the diary is an ordinary vault, made for every account at sign-in (`diary-<user ID>`, named Diary), and each `#diary` line is its own note (or todo) in it, like a message in a chat.

- No `diary` card type. A diary card stored before this reads as a note on its day (`src/domain/payload.ts`), on devices, on the server for AI apps and public links, and in old backups. Nothing on the server was rewritten.
- The journal narrowed to the Diary vault and a day is that day's diary; the Calendar dots days with something in the Diary vault, and its "Diary for this day" link goes there. `/day/<date>` leads to the journal for that day.
- Written while the journal shows another day, an entry is dated that day.
- The vault starts open, like any new vault; the PIN and encryption are the user's choice. AI sees it only when the user opens it to AI.
- The native apps still know the old diary type; they need the same change.

## Implementation notes from the native apps

- The Apple app is in `apple/`: `NotesKit` is a Swift package with the models, SQLite storage, repository, sync engine, API client and crypto, tested with `swift test`; `Notes/` is the SwiftUI app. XcodeGen makes the Xcode project from `project.yml`.
- Card payloads stay raw JSON on the device (`JSONValue`), so fields the native app doesn't know about survive its saves. The SQLite store mirrors the web store: a local write marks the card dirty, and a remote change never overwrites a dirty card.
- Sign-in reuses browser pairing: the app starts a pairing, opens `/pair?p=…&return=app` in a web authentication sheet, and polls until it can claim the session with `token: true`. The server then returns the session as a bearer token instead of a cookie, and the app keeps it in the Keychain. After approving, the page sends the browser to `notesapp://paired`, which closes the sheet.
- Encryption matches the web app byte for byte: AES-256-GCM through CryptoKit, and Argon2id (with BLAKE2b) written in Swift, since Apple's frameworks don't have it. Both are tested against RFC vectors and against values made by the web code.
- The editor is SwiftUI's rich `TextEditor`. Inline formatting is real rich text; blocks are visible markers at the start of a line (`# `, `• `, `1. `, `> `, code fences, `---`). Card links are `notes-card://` links. Photos and anything else the app can't show become placeholders that keep the original node, so nothing written on the web is lost by editing natively.
- The Mac app is called "Notes App" so it can't be confused with Apple's Notes; on the iPhone home screen it is "Notes". The bundle identifier is `dev.notesapp.notes`, signed with the owner's Apple development team.
