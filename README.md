Decisions, the data model and the milestones are in [PLAN.md](PLAN.md).

## Run it

Needs Node 22 or later.

```bash
npm install
npm run db:migrate:local
npm run build
npm run dev:api
```

Then, in a second terminal, start the app with `npm run dev`. The app runs on port 5191, the API on port 8788, and Vite proxies `/api` to it. Rebuild only when you want `dev:api` itself to serve the latest app.

To keep both running after the terminal closes, start them in tmux:

```bash
tmux new-session -d -s notes-app -n api 'npm run dev:api' \; new-window -n web 'npm run dev'
```

`tmux attach -t notes-app` shows their output and `tmux kill-session -t notes-app` stops both.

To try the app without signing in, fill the local server with a demo account and open it:

```bash
npm run demo
```

Settings ends with Delete account, which deletes the open account and everything it owns from the server and from this device, after showing what goes and asking for its email.

## Native apps

How each native app compares with the web app, behavior by behavior, is in [PARITY.md](PARITY.md).

The Mac, iPhone and iPad app is a native SwiftUI app in `apple/`, with the web app's design and behavior: the same journal of bubbles, box, filters, board, menus and pages, on a sidebar on the Mac and iPad and tabs on the iPhone. It needs macOS 26 or iOS 26, Xcode 26 and XcodeGen (`brew install xcodegen`). Builds sign with the Apple development team set as `DEVELOPMENT_TEAM` in `project.yml`; change it to build under another account. Reminders are scheduled by the device itself, with no push setup.

| Command (in `apple/`) | What it does |
| --- | --- |
| `xcodegen` | Generates `Notes.xcodeproj` from `project.yml` (the project file isn't committed) |
| `swift test --package-path NotesKit` | Tests the shared core: storage, sync, the change log, encryption (vault keys, member keys, sealed files, Argon2id), the journal's rules ported from the web with its own test cases, Markdown, backups and the rich text conversion |
| `xcodebuild -project Notes.xcodeproj -scheme Notes -destination 'platform=macOS' -derivedDataPath build/dd build -allowProvisioningUpdates` | Builds `build/dd/Build/Products/Debug/Notes Dev.app`, the dev build (below) |
| `xcodebuild -project Notes.xcodeproj -scheme Notes -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -derivedDataPath build/dd build -allowProvisioningUpdates` | Builds the app for the iOS Simulator |

Launch with `-server http://localhost:5191` to point the app at the local server through `npm run dev` (which passes `/api` on to the API and serves the demo's photos, videos and voice messages, which the API on 8788 can't), and `-page vaults` (or any page's name: `journal`, `today`, `upcoming`, `history`, `calendar`, `timeline`, `photos`, `links`, `files`, `archive`, `templates`, `trash`, `tags`, `settings`) to open it on a page.

**Dev builds sit beside the release.** A build from Xcode (the Debug configuration) or `./gradlew installDebug` is its own app: "Notes Dev" on an amber icon (the released app is "Notes" on green), with its own app ID (`dev.notesapp.notes.dev`), data, sign-in and link scheme (`notesapp-dev://`, the release's being `notesapp://`), so the released app and a dev build are installed on one Mac, iPhone or phone together and never replace each other. The release keeps the plain names: the Release configuration on Apple, the release build type on Android. The apps tell the pairing page (`/pair?return=app-dev`) and Drive's connect (`{"app": "dev"}`) which build asked, and those send it back to its own scheme. The amber Apple icons come from `swift scripts/dev-icon.swift`, Android's from `android/app/src/debug/res`. Keychain items are named after the app's ID, so the two never read each other's. The web's dev server (`npm run dev`) looks the same way: its tab says "Notes Dev" with the amber icon (`src/assets/icon-dev.svg`, put in by a plugin in `vite.config.ts` that only runs there), while builds keep "Notes" on green; being on another address, it already has its own data and sign-in.

The Mac and iPhone apps sign in to Google in Apple's sign-in sheet, with their own OAuth client (type iOS, bundle `dev.notesapp.notes`, which Google uses for Mac apps too; its ID is `GOOGLE_APPLE_CLIENT_ID` in `wrangler.jsonc` and comes to the apps from `/api/config`): PKCE, then Google's ID token, which `/api/auth/google` with `token: true` trades for a bearer session. Once the sheet is closed, or where the server has no such client, they offer the browser instead, pairing with the web app: the app shows a code, the sheet opens `/pair`, and once you confirm the code there the app gets its own session as a bearer token.

The Android app is in `android/`, a native Kotlin and Jetpack Compose app with the same design and behavior: the journal on tabs (Journal, Today, Calendar, Search) with the sidebar in a drawer on a phone, and beside the page on a tablet or an unfolded phone. `core/` is plain Kotlin (the web app's journal rules, Markdown, backups, the change log, sync, the server's API and the crypto, byte for byte with the web's), tested on the JVM with the web's and the Swift app's test cases; `app/` is the Compose app, which keeps each account's cards in SQLite and its session token sealed by the Android Keystore. It needs Android 10 or later. Build with Android Studio's JDK and the Android SDK (`local.properties` names it), from `android/`:

| Command (in `android/`) | What it does |
| --- | --- |
| `./gradlew :core:test` | Tests the core: the journal box, repeats, storage, sync, the change log, saving entries, backups, the rich text conversion and the crypto, checked against values the web app made |
| `adb reverse tcp:5191 tcp:5191` then `./gradlew :app:installDebug -Pserver=http://localhost:5191` | Builds the app against the local server through `npm run dev` (so the demo's photos, videos and voice messages load) and installs it on the running emulator or phone |
| `./gradlew :app:assembleRelease` | Builds a shrunk app, signed with the debug key until there's a release key; it starts much faster than a debug build |

Run Gradle with `JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"`.

### Android releases

Each push to `main` that changes `android/` builds the app on GitHub (`.github/workflows/android-release.yml`), runs the core tests, and publishes the APK as a release named by the day of the commit (`Android 2026.11.24`, tagged `android-v2026.11.24`; a second that day is `2026.11.24.2`). Its version code is the commit count, which only grows, so every release installs over the one before. Its notes list the Android commits since the last release. On a phone, open the release on GitHub and tap the `.apk`. It talks to the deployed server.

It needs a release key, made once and kept out of the repo: `scripts/android-release-key.sh` makes it, asking for its password, adds the four secrets below and starts a release. Without one, the workflow stops and says so. Make the key with Android Studio's `keytool`, which asks for the passwords itself (keep the file and the passwords somewhere safe: an update must be signed with the same key):

```
"/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/keytool" -genkeypair -v -keystore ~/notes-app-release.jks -keyalg RSA -keysize 4096 -validity 10000 -alias notes-app
```

Then add four repository secrets (GitHub, Settings, Secrets and variables, Actions): `ANDROID_KEYSTORE_BASE64` (the output of `base64 -i ~/notes-app-release.jks`), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` (`notes-app`) and `ANDROID_KEY_PASSWORD`. A build from here is the dev app (`dev.notesapp.notes.dev`, "Notes Dev"), installed beside the release; only an older build from here, from before dev builds had their own ID, has to be uninstalled once before the first release installs. Sign-in uses the Google accounts on the phone, through Android's own account picker (Credential Manager): it asks for an ID token for the web app's client ID (from `/api/config`) and trades it at `/api/auth/google` with `token: true` for a bearer session. Google only gives one to an app it knows, so the Google Cloud project that holds the web client needs an OAuth client of type Android for package `dev.notesapp.notes` with the release key's SHA-1 (`"/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/keytool" -list -v -keystore ~/notes-app-release.jks -alias notes-app | grep SHA1`), and two for this Mac's debug key (`keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android | grep SHA1`): one for package `dev.notesapp.notes.dev`, the dev builds, and one for `dev.notesapp.notes`, a release build made here without the release key. Nothing from those clients goes in the app. Where the picker can't sign in (no Google Play services, or the project not set up), the screen offers the browser instead, which pairs with the web app as the Apple app does: it opens `/pair`, and once the code is confirmed there it comes back to the app at `notesapp://paired` (`notesapp-dev://paired` for a dev build). Translation on the device, where the server can't, uses Google's ML Kit, which downloads a language's model the first time.

### Mac releases

Each push to `main` that changes `apple/` builds the Mac app on GitHub (`.github/workflows/mac-release.yml`, on a macOS 26 runner with XcodeGen 2.46.0 checked against its checksum), runs the NotesKit tests, and publishes a disk image as a release named like the Android ones (`Mac 2026.11.24`, tagged `mac-v2026.11.24`). Its build number is the commit count. It talks to the deployed server. It needs no secrets.

The Apple account here is the free kind, which can't make a Developer ID certificate or have Apple notarize the app, so the release is signed ad hoc (no team). It runs with the same sandbox and entitlements as a build from Xcode, but macOS won't open it from a download until it's allowed once on each Mac: open it, click Done when macOS says it can't check it, then System Settings, Privacy & Security, "Notes App was blocked", Open Anyway. Each update asks again, and as each build's signature differs, the Keychain may ask for the Mac's password once to let the new build read the saved sign-in (Always Allow). With the paid Developer Program, the workflow would sign with a Developer ID and notarize instead, and these steps would go. The iPhone app can't be released this way at all: iOS installs only from the App Store, TestFlight, or Xcode onto a phone of the account's own.

## How it fits together

- **The UI goes through `CardRepository`.** It never touches IndexedDB, so the store can change without touching the UI.
- **Stored records are opaque.** Only `id, vault_id, updated_at, deleted, seq` are plain. Everything else is a string produced by `PayloadCodec`: JSON in open vaults, ciphertext in encrypted private vaults.
- **Writes run one at a time.** The repository queues them so overlapping saves can't overwrite each other.
- **Edits are journaled.** Each edit goes to `localStorage` synchronously, is cleared once committed, and is replayed on next launch, so closing the page mid-save loses nothing.
- **Backlinks and search are derived on each device.** `buildIndex` recomputes them from the cards, and they are never stored or synced.
- **Sync never blocks writing.** Edits save locally first and are pushed in the background. Remote changes share the write queue, and never overwrite unpushed edits. That includes an edit typed while a push that lost a conflict was on its way.
- **Each account has its own local database**, and the server checks vault membership on every request. A card someone moves into a vault you aren't in leaves your devices at the next sync (the server notes each move in `card_moves`).
- **Locked cards stop at `buildIndex`.** Lists, search, backlinks and exports are built from the index, so a new view can't leak a locked card by accident. Links must go through `linkTitle`, because a link stores the title it was created with.
- **History lives on the server.** Each push that changes a card extends or adds a version, so history needs a connection but covers every device. Versions hold the same opaque payload as cards, and say who saved them, from which device or through which AI app, and whether the card was in the Trash. `GET /api/versions` lists the newest versions across cards, each with the one it replaced.
- **Undo is a log on the device.** `CardRepository` logs every change it writes (the card before and after, and the action it was part of) in the local database. Undo and redo write the changed fields back, and only while the card still holds what the change left, so they never overwrite a later edit. The server's history is separate. The History page (`/history`) shows the log and, between its entries, the server's newest versions of every card read as changes (`useSyncedChanges`), without the ones this device made, which the log has. A change that came by sync is undone with `repo.takeBack`, which writes its fields back as a new change in the log. The page takes the journal's filter from the same query string (a change matches if its card passed the filter before or after it), and scopes Cmd+Z to what it shows.
- **AI apps get the same protection as locked vaults.** The MCP server builds its index with every vault closed to AI marked locked, and writes through the same push path as devices, so AI edits sync and show in history.
- **Private vaults are encrypted before anything is stored.** The payload codec is a keyring: a card in an encrypted vault is encrypted as it's written, and a card whose key isn't open decodes to a sealed stand-in that can never be saved.
- **Photos and files in an encrypted vault are sealed before anything is stored.** Each gets a key of its own, sealed with the vault key in a header with its name, type and shape, and the file follows in 1 MiB pieces (`src/crypto/attachmentSeal.ts`). This device's storage, the server and Google Drive keep only that; the server marks it `sealed` and knows nothing else of it. Encrypting a vault, or stopping, copies each one under a new ID, sealed or opened, and deletes the old one once the copy is up (`src/photos/reseal.ts`).
- **A shared encrypted vault's key never reaches the server unsealed.** A member's device makes a P-256 key pair and keeps the private half wrapped under the member's own PIN, on the server with their membership; the owner's device, once the owner lets them in after comparing a code made from the public half, seals the vault key to it (ECDH, HKDF, AES-GCM, bound to the vault). Until then the server sends the member nothing in it. Comments in an encrypted vault are sealed with its key too (`src/crypto/vaultKeys.ts`, `server/members.ts`).
- **Turning encryption on can be picked up again.** The device notes that a vault is being encrypted before it tells the server. If the tab closes or a sync fails before every card is stored again and the server's readable versions are dropped, the rest is done the next time the vault is opened on that device (`src/state/encrypting.ts`).
- **Dates are local calendar days** stored as `YYYY-MM-DD` keys, never UTC instants.
